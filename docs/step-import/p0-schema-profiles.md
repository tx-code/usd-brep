ISO SMRL附件获取本轮未完成，下载残片未解压、未用于结论。它仍是规范身份的独立补证工作；不应为取得全部历史附件反复暂停已有具体字段和依赖闭包的设计。若未来决定采用某实现发布稿作为明确版本的输入profile，必须准确命名其范围，不能顺带声称完整ISO符合。

## 2. 已经改变清单的差异

| 问题 | 纠正后的设计依据 | 对现有文档的修改 |
|---|---|---|
| conversion-based单位槽 | AP214e3文件将dimensions转为DERIVE；AP203e2/AP242e1—e3文件仍显式 | `NAMED_UNIT(*)`与`NAMED_UNIT(#dim)`按profile分开；SI仍为派生槽 |
| description可缺省 | 较新版所核字段OPTIONAL；AP203e1修改副本中多个同名字段required | `$`正例绑定profile，新增required反例，不把空串当缺失 |
| 专用SELECT | AP214/AP203旧文件可能以继承属性＋WHERE限制，同名新SELECT并不存在 | 槽数相同不代表类型声明完全相同；按该文件检查 |
| AP242 OID | 官方表的`442 3 1 4`为e2，`442 4 1 4`为e3 | 更正先前e3线索的误标，完整OID保留 |
| AP214 OID | MBx页面、文件自述、STEP Tools说明不一致 | 冲突未解决；不截尾、不按数字猜版次 |
| APD字面量/量词 | 不同AP/edition的RULE常量和数量条件不同 | 不从HEADER名字自动生成APD值，不统一去后缀或改大小写 |
| 全局单位规则 | AP203e1修改副本要求三类单位各一；AP214e3要求长度/平面角各一；不能移植到其余文件 | canonical正例给mm/rad/sr仍是项目样件选择；反例按实际触发规则分桶 |
| 产品及uncertainty反向规则 | 分类、owner、context角色、同名uncertainty等不只靠前向几何图判定 | 38类主清单不宣称完整闭包；必要反向关联与计数另登记 |

上述更正已有固定文件的文字依据；不存在“运行已通过”的含义。数学真值中的坐标、面积、体积不受这些字段差异改变，但对应的合法STEP文本必须分别设计，不能只替换HEADER。

## 3. 三种检查范围必须分开

| 范围 | 所检查的对象 | 结果的用途 |
|---|---|---|
| 文件的全局EXPRESS规则 | 原RULE指定的全文件实例集合及其量词 | 记录针对哪份schema、哪些规则检查；不能把全文件量词改为根局部后称完整AP符合 |
| 所选导入profile的必要检查 | 所选根、完整依赖、逆向使用/单位/context、已证明影响它的附加内容，以及明确列入的源约束 | 决定该请求能否交Accepted。已知必需失败、未知影响或未核条目均阻止交付 |
| 完整AP符合性 | 对精确规范版本及适用交换范围的全部要求 | 单独资格；本轮未授予，也不是“几何正确”或任一reader返回成功的别称 |

沿用总体规格的范围政策：全文件语法/实体ID歧义不能通过选根绕开；未选内容按影响分类。不能因为发现一个管理RULE就自动要求所有未选零件的管理信息全部合规，也不能因为它没有被face直接引用就忽略。

每条发现的规则应明确归为以下之一，并给出依据：所选内容必要；在本profile严格限制下不触发；经证明仅影响未选/附加内容；尚无法判定。最后一种不允许冻结为可接纳profile。若来源只支持一个实现稿的结论，记录其文件身份，不能扩展成所有历史AP的结论。

AP214的part分类/id-owner约束是当前必须处理的具体例子。若把它列为某profile的源符合性门槛，最短组织路径还引出ORGANIZATION、ORGANIZATION_ROLE、APPLIED_ORGANIZATION_ASSIGNMENT及后续规则，详见[AP214报告§5](p0-ap214-provenance.md)。若仅验证几何转换子集，则须先证明被排除管理内容的影响界限并明确声明检查范围；**本轮没有替这项尚未完成的证明填“无影响”。**

EXPRESS的TYPEOF/USEDIN、INVERSE、SET/LIST身份、UNIQUE、函数调用与三值逻辑不能只用字段数代替。具体判断证据不足时按项目保守政策返回未判定，不能把UNKNOWN当作已证明True，也不把它伪报成已经证明的源错误。

## 4. 一个可接纳profile必须具备的记录

下面是P0清单的记录合同，仍是设计文档，不是新增公开接口或已实现的JSON格式。

| 记录组 | 必需信息 | 冻结条件 |
|---|---|---|
| 身份与适用声明 | 完整FILE_SCHEMA名/OID；载体版次；schema文件URL/hash/自述/修订；允许的无OID情况；冲突状态 | 每种接纳路径有明确依据。裸名不能自动选“最新”；调用者若可显式选profile，也须单独设计并记录，不能覆盖矛盾声明 |
| 字段与complex签名 | 每一实体/constituent的继承、局部/显式/optional/derived、槽位、SELECT、聚集、枚举 | 同名不同版差异逐条封闭；已知额外subtype不会被丢弃；原始类型和位置可追溯 |
| 必要依赖 | 根选择、前向引用、相关逆向角色、单位/context及可能改变解释的包装/关系 | 未知或未支持的必需分支有准确拒绝；资源有界，不能靠只选最大solid绕开 |
| 约束及影响 | UNIQUE/WHERE/INVERSE/RULE及被调用函数；触发条件、量词、作用范围；必要/不触发/无影响/未判定分类 | 每项分类有来源和正负控制。新增category/organization等会重新展开闭包，不能以主图清单长度证明闭包完成 |
| 几何及目标映射 | 源定义、单位/参数/方向、source→neutral→native对应、owner/window/UV/tol、保形规范化 | 对接既有数学真值和SMLib审计，不将AP规则通过当native正确性证明 |
| 证据与拒绝 | 规则/字段来源、检查版本、绑定case、预期阶段/诊断、NotRun/通过/失败/未判定 | 文档已核、代码已实现、动态通过分别标记；无法满足的项目不能省略或填零 |

接受registry只包含完成相应阶段证明的profile；研究候选表不是registry。所有输入记录仍保留原始身份/字节/位置；对未获接纳资格的profile可提供识别和诊断，不生成本次模型。

## 5. 后续先做什么

后续更新：用户已明确要求优先完成AP203e2首profile的必要规则与依赖闭包。对应[静态合同](ap203e2-planar-profile.md)及三份明细已完成：封闭准入36种simple叶／六complex签名；N2635全部47条RULE分为5项必查、1项条件必查、41项有守卫的不触发；局部祖先/WHERE/INVERSE/UNIQUE和函数、反向索引逐项登记。该首profile所有壳面均为ADVANCED_FACE，普通FS暂不准入，原因和源文件缺陷边界明确记录。以下顺序是原研究计划，前两项的这一窄profile静态交付已完成，不代表动态资格通过。

建议先用**203e2-N2635作为第一个规则闭包分析候选**：它已有官方当前发布文件、固定项目镜像同hash和精确行号，便于复查；这只是研究顺序，不把它定为产品默认，也不声称其完整符合性比其他协议更高。AP214、AP242仍是已确认的首版目标，按增量补齐各自profile。

1. 按上述记录合同，完成一个direct单零件、LINE/PLANE、ABSR/MSSR的最小必要字段和规则闭包，逐条标明影响及不触发依据。优先消除当前直接阻塞条目，不继续扩大到完整PMI或所有历史版次。
2. 将同一个独立几何真值分成各profile自己的合法记录布局，写明最小产品/context管理图、HEADER/APD值、必要单位及complex签名；在尚不编码阶段只定义文本/数据应包含什么。
3. 为每个必要条件配对正例与单一变化反例；现有主目录已扩至63条Defined/NotRun，三份来源审计的细分建议在落实时关联到稳定ID，不把建议数量当fixture数。
4. 冻结测量器计划、误差证明和资源/取消边界后，才具备相应P0退出证据；实际parser/fixture/oracle/native运行仍待用户后续编码授权。

当前状态：AP203e2首个窄profile的静态闭包和允许签名完成；其他profile、完整Part21映射/规则执行与native证据未完成。P0未退出，63条主用例和profile细分控制均未运行，运行时profile未获接纳资格；设计基线0.1保持原字节不变。
