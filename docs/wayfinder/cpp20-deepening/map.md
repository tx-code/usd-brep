## Destination

形成全仓 C++20 深化方案：以源码证据确定哪些约束、固定描述和派生数据最适合移到编译期，
明确选中方案的兼容性、构建代价与分批验收路线。终点是可实施的决策路线，不是语言特性的使用清单。

## Notes

- 用户已确定全仓自有目标统一 C++20；本专题在该基线上继续深化，不重做标准切换。
- 用户的明确偏好是“能编译期就编译期”。优先调查让错误尽早被编译器拒绝、让固定事实只维护一次的方案，
  也记录可消除的运行期开销；不能仅凭写有 `constexpr` 就声称已在编译期执行。
- 本轮请求是开专题并调查最佳落点；按 Wayfinder 默认先规划，不修改产品实现。
  具体重构、接口变化及批次安排通过专题票决定，未决定事项不记为用户批准。
- 覆盖内核、SM_API、Python 绑定、STEP 源语义及相关构建/验证入口。固定的程序描述与外部输入分别分析：
  编译期证明登记表正确，不能代替对用户 STEP 文件、运行期几何或动态所有权的验证。
- 每次会话先读本地图；讨论票使用 `grilling` 和 `domain-modeling`，模块取舍使用 `codebase-design`，
  代码事实按所涉范围使用仓库技能。新验证范围使用 `usd-brep-test-selection`。
- 事实优先从当前源码核实。需要标准或工具链外部证据时，新增具名 research 票，依 `research` 技能执行；
  不把未核实的标准库常量求值支持当作已具备能力。
- 使用本地 Markdown tracker；讨论与文档用中文。后续实施按可独立审查的批次提交，不创建远端 issue/PR 或自动推送。
- 初始扫描固定点为 `602b082`；[初步代码线索](initial-scan.md)只是建图材料，不是已批准的迁移方案。

## Decisions so far

尚无已关闭专题票；上面的用户明确偏好是输入约束，不代替后续技术取舍。

## Not yet specified

- 仓库基线盘点还可能暴露其他高收益登记点与类型约束；见到具体证据后再增票，不先按特性名称铺满任务。
- 若模板审计发现无法由现有类型模型证明安全的实例，其隔离、修复或替代方案待具体实例明确后再拆票。
- 若所需常量求值能力遇到标准或实现限制，再据实际阻碍展开工具链研究或可丢弃原型。

## Out of scope

- 本轮直接修改建模算法、容差政策、严格导入接受范围或所有权合同。
- 将运行期文件、几何和可变对象图的检查宣称为编译期已证明。
- 仅为采用语法而机械替换比较运算符、循环、宏、全部容器，或重写整个句柄体系。
- 修改 vendored 上游，或将未验证的平台/工具链支持写成已验收。
