## Question

在用户“能编译期就编译期”的偏好下，如何取舍编译期错误保障、固定工作的前移、接口简化和构建成本？
是否允许为这些收益重构内部类型及数据表示？稳定 SM_API/Python 合同、公开 C++ 布局与 ABI 各自如何约束？

应明确原则与例外的决策方式；尚无构建测量时不虚设数值阈值。
明确哪些调整可作为内部实现选择，哪些必须带具体影响另行确认。

## Blocked by

无。

## Context

[初步代码线索](../initial-scan.md)。用户已确定 C++20 基线与编译期优先。

## Resolution comments

2026-10-18，用户明确答复“允许破坏性改动”。据此，候选可调整接口、内部类型、数据表示和 ABI；
不再以稳定 SM_API/Python 合同或既有 C++ 布局作为不可突破的筛选门槛。
具体方案仍需给出调用者影响、迁移办法和验证要求，不能把兼容性许可当成具体方案已获批准。

随后用户明确选择“编译期保障优先，测量后控制构建成本”。本票据此关闭，采用以下门槛：

- 固定事实能被可靠地生成或证明时，优先编译期保障。候选既可减少运行期固定工作，也可使错误用法编译失败；
  是否值得采用以具体错误和派生关系为依据，不按使用了多少 C++20 特性计数。
- 可调整接口、类型表示和 ABI，不要求保留旧接口或为旧表示增加兼容层。
  候选须列出受影响的调用者、所需迁移和验证，尤其说明所有权、诊断及数值语义是否变化。
- 不预先设置未经测量的编译时间或内存硬上限，也不因预计增加编译成本就默认退回运行期。
  应测量编译时间、编译器内存与目标大小，先考虑减少公共头中的重复计算、集中实例化或调整翻译单元归属等手段。
- 若实际工具链能力、资源限制或收益证据不足，保留具体观测并另作取舍，不把未实现的编译期保障写成已完成。
- 本决议解除的是候选设计的兼容性限制，并确定成本取舍原则。具体重构仍由后续专题票选择；
  当前地图继续遵循调查与决策的终点，不直接修改产品实现。
