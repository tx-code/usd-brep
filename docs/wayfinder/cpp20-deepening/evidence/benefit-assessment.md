# C++20 候选收益评估

2026-10-18；用户补充“最好有明确的收益”后，对[收益门槛](../tickets/01-priorities-and-compatibility.md)的应用。
事实依据为[代码基线](code-baseline.md)及其源码指纹和编译观察。本文件没有新增性能测量或产品实现，
列出的收益是候选实现需要交付的目标，不是已经取得的结果。

## 当前排序建议

| 候选 | 具体场景及当前发现时机 | 拟交付的收益 | 验证办法与当前判断 |
|---|---|---|---|
| STEP 固定 schema 目录 | 开发者登记重复类型、无效父类型或继承环，当前在相应 profile 首次构造时发现 | 固定元数据错误在构建时拒绝；预生成名称索引、祖先闭包和展开字段，消除对应运行期推导 | 有效目录编译通过，逐项注入坏描述应编译失败；四个 profile 的查询和诊断保持约定行为。收益对象具体，优先深入；尚无导入提速数据 |
| SmTArray 存储及算法契约 | 字节存储、复制、清零和删除有不同前提，主要依赖注释；实际存在按值嵌套数组 | 对确实不满足前提的实例，在对应存储或算法入口拒绝；需要非平凡构造的实例迁往满足生命周期要求的表示 | 先审计实例，区分可接受类型和必须迁移的调用，再做正反编译例及生命周期验证。潜在保障价值高，但尚未证明某个现有路径已发生内存破坏；不能先套一个 trait 结案 |
| 固定有理数和质量预设 | 非零 Rational 构造当前不能常量求值，固定配置仍通过运行期工厂及验证表达 | 固定分母为零、范围溢出或配置组合错误在构建时拒绝；固定规范化和派生值不再运行期计算 | 编译期正反例，固定值与运行期等价性，动态输入仍保留真实诊断。保障目标清楚，运行时间收益未测，排在目录之后讨论 |
| 状态、协议及绑定选项登记 | 多处描述同一事实容易同步遗漏；但当前原生与 Python 的 26 个状态名称已匹配，协议身份已有 constexpr 数据 | 只有在唯一来源能够生成消费者或检查完整覆盖时，才减少以后新增条目的漏改风险 | 在唯一来源增加/删除条目后，消费者自动跟随或编译失败。没有当前遗漏证据，不按已修复缺陷计收益；不因表已 constexpr 就单独安排一批 |
| 静态尺寸入口 | 某些曲线构造有最少控制点数等合同，但 Python、STEP 和许多原生调用的尺寸在运行期才知道 | 让真实固定尺寸调用在编译期拒绝错误数量或参数种类 | 先找到实际固定尺寸调用及其重复检查，说明受益面。当前未统计这类调用，暂不宣称能显著减少动态检查 |

该排序体现证据清晰度和预期保障，不是性能排名，也不是具体迁移方案的批准。
已有 `StepRuleCatalog.h` 编译期检查应保留；重复建立同样的保障不算本专题新增收益。

## 固定目录应承诺什么

[StepCatalog.cpp](../../../../source/STEP_SEMANTICS/src/StepCatalog.cpp) 的 `Catalog::Catalog()`、
`ValidateProfile()` 和 `Schema(ProfileKind)` 给出了可以比较的改前行为。
若选择该候选，至少按下面的结果验收，而非按新增多少 `constexpr` 验收。

| 改前 | 目标结果 | 验收证据 |
|---|---|---|
| 重复声明、无效父类型、继承环在使用到该 profile 时才报内部错误 | 所有已登记固定 profile 都在构建时检查，不依赖运行期是否访问该 profile | 合法最小目录和真实目录编译通过；各类错误的独立负例在目录构建入口拒绝 |
| complex facet、SELECT、枚举和派生槽等固定登记关系由运行期检查 | 已纳入迁移的固定关系由同一静态描述检查，新增条目不能绕过检查 | 对缺失 facet、无效引用和没有对应继承字段的派生槽给出负例；明确仍未覆盖的约束 |
| 首次使用时构造名称索引、遍历继承关系、展开字段，并分配相关动态存储 | 已迁移的固定派生数据在程序运行前就存在，不再做相同 DFS、展开和索引构造 | 查验存储及初始化路径；记录是否仍需兼容表示或动态适配，不能把残留构造隐藏在查询接口后 |
| FieldBinding 借用目录内字段和 origin 视图 | 查询得到的描述具有明确寿命，profile 身份、继承字段次序和诊断来源符合合同 | profile 隔离、字段绑定次序、只读视图寿命和外部 STEP 诊断回归 |

“消除固定构造”是实现结构目标；“导入更快”是另一项需要测量的结果。
当前四个 profile 分别使用函数内 `static const Catalog` 缓存，重复导入并不重复构造同一目录。
因此即使完成迁移，也不能把首用构造耗时的减少直接当成所有导入的同等收益。

测量应在同一工具链、配置和机器上区分：新进程首次取得目录、进程内重复查询、完整导入。
记录耗时和目录相关分配；对完整导入给出固定输入、重复次数及分布，不能用单次微基准代表几何算法总耗时。
同时记录干净构建和修改目录后的增量构建耗时、编译器峰值内存、库与可执行文件大小。
共享实现应集中固定数据的生成，避免每个公共头消费者重复支付编译期计算成本。
具体工具链、样本和执行命令由[编译期迁移怎样证明等价并分批验收](../tickets/06-validation-and-batches.md)确定。

## 不计入本轮收益的说法

- 外部 STEP 数据仍是运行期输入。固定目录正确不等于用户文件、数值几何或所有权已被编译期证明。
- `SmTArray` 的类型 trait 探针只说明类型属性，尚不能证明字节复制、清零或历史嵌套实例安全。
- 将已会被常量折叠的分支改写为 `if constexpr`，没有额外证据时不声称提速。
- 将已有 constexpr 默认值、列表或纯转发接口换一种语法，没有新增保障时不作为独立收益。
- 调查优先级不等于已取得收益；实施后只报告实际通过的保障和实际测到的变化。
